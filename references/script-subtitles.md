# 从素材到口播定稿与显示字幕 SRT

用于用户给出视频、主题、聊天修改记录后生成口播稿，以及只交稿件/字幕的任务。配音操作与实测校时另读 [剪映配音](jianying-voice-ai-edit.md)。**当前配音入口是保留自然标点的整段文稿、默认一个文本片段、一次朗读；已证实单次上限时按剪映流程分少量长块，合并真实导出后再定轴；本文件的分句、字数、标点限制只作用于最终显示字幕，不可拿分句SRT去逐条生成配音。**

新稿/网感润色先按 [文案选择规范](internet-copywriting.md) 确定输入状态、人群任务、主要目的、证据与正文路线；本文件负责交互定稿和SRT构建，不重复维护钩子库。

## 写稿与交互

1. 先看上传素材，给可用镜头标素材ID和源片起止点，区分真实功能、成品、等待、失败与缺失步骤。先依据真实内容和用户主题写稿，不能从一个标题补造演示结果。素材不足时照常完成有依据的段落，并标明补录/示意位置。
2. 正文与证据明确后，按 [只替换省略号规范](copywriting-library.md) 选完整原句，仅填省略号，其他文字、数字和标点不动。用户指定某个成句则逐字采用，禁止擅自换成其他钩子。实际朗读检验开头吸引点，不为3秒目标改写成另一种开头。
3. 按已选正文路线串起短稿：可走任务跟做、结果带路、失败修复或同题对比等；不把所有素材强套同一公式。教程步骤是否展示按任务范围决定，不把口播写成无用的逐项菜单朗读。结尾必须有一个具体、自然的行动引导，例如试做一个真实任务、收藏本次步骤、评论想解决的相关问题；已有明确引导沿用，除非用户本轮要求删除。
4. 交付逐句可改的口播稿：稳定ID、台词、对应素材/画面、待核实项。收用户修改后做定点替换，保留已认可的内容；润色要保留事实、语气与意图。未完成的文案交互不得跳到配音。用户已明确成稿或授权按稿继续时，不重复求确认。
5. 定稿后保留独立 narration_text 完整文稿；配音后按真实声音做显示字幕分句，只字幕任务可独立分句。每条最多两短句；一个必要句中逗号可以连接两短句。句末去掉句号、逗号、分号等标点，**问号和叹号可保留**。不要为了时间、固定字数或视觉节奏机械切碎台词。

## 分句标准与可测边界

- 逐条出现、语义完整、长短适中。建议每条约8–26个中文可见字，通常2–5秒；这是编辑起点，不是强制时长或硬字数目标。先按实际朗读和画面判断，再人工改写；别给个别长句偷偷缩字号。
- 同一条超过两短句或两个及以上逗号，重新拆写；连续多个句号/问号拼在一条也不能假装是一句。不要一条四个字，更短的词块也应避免。品牌独立强调、故意停顿、问答回应等确有必要时，用稳定ID记录具体例外理由，不能普遍豁免。
- 工具默认将少于5或多于30个可见字母/数字判为待修订。英文按字母计数，所以英文较多时按实际阅读负担调整`--max-chars`；这只是长度警戒，不代替中文语义判断。字幕超过两行要先调整文案或统一排版。两短句之间自然的短分句无需各自凑满字数。
- “前3秒钩子”“结尾引导”“每句自然”“对应画面真实”必须人工核对。程序只检查格式、长度和已声明时间，不会证明创意质量或同步正确。

## 定稿 JSON → UTF-8、CRLF 的 SRT

保存一份定稿源，稳定ID跟随台词修改；不要把数组序号当永久ID。工具不会替你自动拆句、删标点、改文案或生成配音。

```json
{
  "script_status": "final",
  "revision": "v3",
  "timing_source": "provisional",
  "cues": [
    {"id": "hook", "text": "转正答辩还在手动排版？"},
    {"id": "benefit", "text": "先把经历整理清楚，再生成汇报大纲"},
    {"id": "cta", "text": "收藏这份步骤，下次汇报跟着做"}
  ]
}
```

用户仅要建议字幕或确需预排轴时允许估时，但必须显式开启，文件名标“待配音校时”；不把此SRT作为默认配音输入：

```bash
python3 scripts/build_jianying_srt.py /absolute/path/定稿.json /absolute/path/字幕_待配音校时.srt --allow-provisional
```

工具同时写`.manifest.json`，记录定稿ID、文本哈希、时间来源与例外理由。配音完成后，以导出音频/剪映音轨实际朗读位置填入每句`start`和`end`，单位秒；将`timing_source`改为`measured`，可加`audio_source`说明实际文件。每句必须都提供时间；同一时间源重建字幕、镜头和画面对照，不能混用部分估时与部分实测。

```json
{
  "script_status": "final",
  "revision": "v3-measured",
  "timing_source": "measured",
  "audio_source": "/absolute/path/剪映配音.wav",
  "cues": [
    {"id": "hook", "text": "转正答辩还在手动排版？", "start": 0.08, "end": 2.45},
    {"id": "cta", "text": "收藏这份步骤，下次汇报跟着做", "start": 2.58, "end": 5.6}
  ]
}
```

短句例外只在确有必要的对应cue增加`"short_exception": "品牌名称单独强调，已确认保留"`。改过SRT正文或时间后旧manifest将失配，应回源JSON重建，不能拿旧例外绕过检查。

```bash
python3 scripts/build_jianying_srt.py /absolute/path/定稿实测.json /absolute/path/字幕_实测.srt
python3 scripts/validate_srt.py /absolute/path/字幕_实测.srt --jianying --manifest /absolute/path/字幕_实测.manifest.json --duration-seconds 48
```

已提供建议时间也可用`start/end`；无时间时才使用`--cps`（默认5）和`--gap-ms`（默认120）估时。上述间隔只服务建议字幕预排，不是最终气口标准，也不用于剪映逐条配音。实测校时后仍要听审、看字幕；剪映导入后核对条数、顺序、汉字、换行和时间，文件可解析不代表已导入成功。

用户供时但未取得真实音频时，原样保留供时，仍使用`provisional`，不能假称本轮已实测；此时`timing_estimated_by_builder=false`表示工具没有估时，不表示已核验同步。现有manifest不细分供时来源，另在项目记录写明“用户供时、无音频、未校验”，不要因此改写台词或重新估算时间。

旧版`--commas-only`维持原行为，会拒绝问号和叹号；新版任务使用`--jianying`，两种模式不要合用。同名文件默认不覆盖，修改后用新版本名；有意替换时显式`--overwrite`并先保留获批版本。
