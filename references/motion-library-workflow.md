# Motion, source editing and sound

Use this guide for editing/packaging tasks. Script-only, caption-only and voice-only requests do not expand into visual production. Protect current user requirements for direct cuts, still reading sections, approved sound or no sound.

## 1. Select capabilities before implementation

The four recommended projects have different roles: HyperFrames is an HTML/CSS/GSAP engine, Remotion provides React-engine guidance, Video Use supports source/speech-aware processing, and Video Shotcraft supplies concrete shot recipes and sound-design guidance. Use one main render engine and one output clock. A second engine is only for an explicitly justified local asset, not another full-film pipeline.

Check installed entries through portable discovery. If a recommendation was declined or is missing, do not force its reading packet. Base editing/planning can continue; explain when a specific effect or renderer requires an unavailable tool. Missing recommendations never authorize installation. Add the selected features to the project state before dependent code: engine_remotion / engine_hyperframes / source_processing / shotcraft.

For an installed Shotcraft, inspect its current library index to locate cards and exact demos; upstream file layouts may change. Read selected cards/implementations in full before adapting. Do not reproduce an effect from its name alone or claim a dynamic demo was seen after only reading code.

## 2. Design the whole sequence

Divide the actual story into relevant sections. For each record the information task, source/time interval, voice window if any, primary motion, transition, settled reading time and sound. Use varied but coherent movement: materialize content, reveal a result, transfer spatially, focus a detail, then settle. Motion serves meaning; do not force movement on every subtitle.

Show the whole page/context before a detail push-in. Similar source pages share scale/anchors. Keep one dominant action per shot, with time for entry, main action, settle, reading and exit. Declared exposure/settled intervals of 0.5s are only a floor. Use longer for complex UI/text. Avoid cuts back and forth that fragment one complete operation.

If the user requested rich packaging, implement effects/motion/transitions/sound across applicable story sections rather than only the intro. Still reading, precise operations and explicit direct-cut/no-sound sections can remain quiet; record the reason. No decorative motion merely to prove a skill was read.

## 3. Sound and rights

Read the selected upstream sound-design/aesthetic/attribution files. Do not assume a fixed number of bundled sounds or a fixed path from an old snapshot. Verify the selected asset's license and retain required attribution; do not redistribute unknown-source audio.

Align the audible event after its lead-in silence to the actual visible response frame, motion peak or settle. Do not merely place the file start at a spoken “click.” Music, narration, source sound and SFX stay on independent tracks. Group actions normally need one intentional event, not machine-gun sounds for every row.

No narration still permits approved music/SFX. A fully silent request stays silent. Removing a category of SFX does not remove protected music/source audio, and broad style guidance must not restore explicitly removed sounds.

## 4. Evidence and completion

Record card/source path, actual adoption (candidate / partial / implemented), output frame/time, reading hold, sound offset, protected items and evidence. Check transition before/middle/after, long text, final settled frames and real playback. Follow an actually used skill's final review requirements within current authorization and available review tools. If independent review is unavailable, say so.

Do not call a code review, static frame, partial playback or helper test a completed full-film viewing/listening review. Export properties and content/quality review are separate evidence.
