# 导出、音频与渲染故障处理

按触发场景读取相应部分。先服从最新交付要求；用户接受清晰1080p后，不继续消耗资源渲染先前的4K版本。2026-10-23最新默认：1080p、60fps、MOV；用户最新指定优先，历史4K/MP4不是当前默认。

## 正式导出的最短可靠路径

1. 锁定当前源码、字幕/镜头时间轴和音频资源，记录实际时长、总帧、fps与哈希，保留可恢复基线。导出前不顺手改创意内容。
2. 明确目标尺寸、fps、容器、声音和输出位置。默认横屏1920×1080、60fps、MOV，竖屏1080×1920。普通成片使用H.264/AAC，透明层或指定母版再选ProRes4444/422。若引擎只能生成MP4，先正常渲染，再用ffmpeg无损重封装成MOV并验证major_brand为qt；禁止只改后缀。用户指定MP4时按MP4交付。质量以正文/字幕清晰、声音正常为准；不默认巨型母版。原图/录屏较低分辨率时不声称升采样创造了新细节。
3. 先用目标参数检查动效中间帧、视频/GIF、字幕、隐私区和首尾，再渲染短段测实际速度/资源/音轨。新脚本确认API参数名与已安装版本一致，例如`renderMedia`的落盘参数为`outputLocation`；函数返回、打印“已导出”不证明文件存在。JS导出脚本可用checkJs或TypeScript对照已安装API检查，提前发现被静默忽略的参数。
4. 检查短段存在且可解码，再整片输出。保存实际渲染进度，不把编码比例误报为完成，也不据初始速度给不可靠ETA。渲染时继续不依赖它的文档工作；用户更改目标后停止已不需要的任务。
5. 对最终文件检查尺寸、平均/标称帧率、**实际解码帧数、逐帧显示时间戳**、时长、音轨、体积和完整解码；正式导出运行 `validate_export.py --check-cadence --decode`。恒定60fps应每帧相差1/60秒，不能只看头信息。B帧用解码后的display PTS/best-effort时间戳检查，不能误把编码包重排当掉帧。
6. 再查开头、结尾、删段接缝、关键操作、源片循环/媒体加载处；用连续帧/帧哈希排查**本应持续运动**处的异常冻结、旧帧回放和循环重置，并实际1×观看动态片段/目标播放器。完整视觉回看与连续听审分别记录；只测时间戳/解码不能声称播放体验全部验收。已发现卡顿/缺帧必须修复并复验，不能交付后说“文件写着60fps”。

MOV重封装示例（路径替换为本期，避免覆盖旧版）：

```bash
ffmpeg -n -i render.mp4 -map 0:v:0 -map 0:a? -c copy -movflags +faststart final.mov
python3 scripts/validate_export.py final.mov --container mov --width 1920 --height 1080 --fps 60 --duration-seconds 48 --frames 2880 --check-cadence --decode
```

48秒仅为命令示例，使用本期实测值。60fps描述输出时间基准，不冒称低帧率源素材变成原生60帧。

可用`../scripts/validate_export.py`。脚本只证实媒体结构/可解码性，不能证明语义、音色、字幕清晰度或审美。

## 实录不慢放与卡顿的判别

- 录屏默认1×且禁止降速凑配音；录屏时长不足优先扩选真实前后文、合并相邻镜头、跨句连续展示，或接真实结果静帧供阅读。禁止把动作拉慢、循环/重复帧伪装成连续操作。明示的阅读静帧与原片自带静止状态不是掉帧。
- 低帧率录屏转60fps时按原时间采样产生重复源帧可能正常，不冒称原生60帧，不因此给受保护操作做光流补帧/改速。运动画面在源片中已卡顿时，应换干净素材或补录；输出时间戳整齐不能消除源片卡顿。
- 区分源录制卡顿、合成冻结/旧poster、编码/拼接时间基准错误和播放器解码不足。定位到哪一层就在该层修复；不能把任何预览卡顿都归咎于硬件，也不能用全片插值掩盖缺录。
- 正式无卡顿验收要同时有：速率审计、实际解码帧数与连续display PTS、关键动态连续帧、实际1×播放观察。未看完的范围明确标待核验，不做设备无关的绝对播放承诺。

## 改帧率：保秒数，不改语速

- 从时间单位识别起：秒、音频采样、源媒体帧、剪辑基准帧、目标输出帧不可混用。`目标帧=秒×目标fps`；输出总帧随fps变化，实际秒数保持。
- 只改Composition的fps会令硬编码镜头、字幕、trim、Loop和Freeze整体错位。优先以秒/统一时间表驱动；已有工程大量基准帧时，可建立一个清楚的基准时钟适配层，把所有Sequence/Loop/Freeze/媒体trim映射到目标帧。
- 动效按分数基准帧计算，不能先floor到旧帧后复制。用至少一组相邻奇偶输出帧检查新增帧确有运动；录屏/GIF自身帧率较低时出现重复源帧正常，不伪造其原始帧率。
- 声音在真实输出时钟播放，旁白/BGM仍为1倍速；音效事件按源时间映射，不能在适配层和声音组件中各乘一次比例。视频trim和playbackRate也不可重复缩放。
- 同一实际秒数比较旧预览与新输出，检查镜头切点、字幕、背景相位、GIF时间、音效峰值和最后0.5秒。改分辨率时用设计画布缩放或可适配布局，避免只改宽高导致内容缩在左上角。

## 慢速/低沉“怪兽声”：先定位再修

按“原始整段导出音频（旧案可为逐句音频） → 必要处理后的主轨 → 实际框架离线短段 → 实时预览”逐层对比同一段：

| 证据 | 下一步 |
| --- | --- |
| 原片已异常 | 核对来源、原生配音速度与音色；未经授权不换声线 |
| 原片正常、主轨异常 | 查采样率是否真重采样、声道/格式是否误读、拼接及变速链；不能只改采样率标签 |
| 主轨正常、离线输出异常 | 查fps/trim/playbackRate、重叠音轨、声音适配是否重复换算 |
| 离线正常，仅Studio异常 | 检查实际播放速度、缓冲/解码、资源URL与格式缓存，再有针对性刷新 |

- 同名资源从单声道换成立体声或重写格式后，旧解码缓存可能混用。生成不可变内容哈希URL并更新引用，重新解码；原始文件和声线保持。音效/BGM同样适用。
- 以相同采样区间、采样数、波形/相关性和实际声音片段核查。相关性高只说明信号接近，不自动证明观众听到的音色正常。
- 未抓到异常现场且离线正常时写“证据更支持预览/解码问题，未复现现场”；不能把“可能卡顿”说成已证明原因，也不能用盲目提高音调掩盖。

## 密集素材与渲染速度

- 白块/超时先看资源是否404、字体是否失败、是否有视频错误，再判断解码/内存压力。为墙面按目标实际显示像素生成等比代理，记录清单并保留原图；不把所有5K原图直接重复解码。
- 从单并发或低并发短段开始。若稳定但慢，再一次只比较一个变量：并发、浏览器/GL或编码参数；记录实际耗时与画面差异。GPU设置不保证更快，不因为参数名听起来更好就全片重跑。
- 目标参数短段、实际落盘检查、最终全片解码分别有证据；代理、渲染器、编码方式变化后，检查文字边缘/材质/颜色，没有新问题不继续调参。浏览器资源回收告警与缺帧/解码失败分开记录；只有已定位的告警可分类，仍需以最终文件验证闭环，不能一概忽略console.error。
- 渲染失败保留源码、诊断和可复用素材；修复具体原因后只做必要复验。收到新的分辨率/交付要求时先重算输出范围，避免继续无用工作。
